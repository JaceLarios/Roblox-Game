Seventeenth pass, same day, one large multi-part ask covering nine separate changes at once: un-placing from the fuse pad, gating passive income behind five physical per-plot pads instead of raw inventory, a Blue/White/Purple/Green/Red signature palette, Pet-Simulator-style UI inspiration, a Shop UI replacing the gamepass-only panel (passes + codes + coin-purchasable pets), a base speed increase plus a new Speed Boots upgrade, a second ("Most Dedicated" playtime) leaderboard face, a bigger Inventory popup, and fixed 5/15/30/60-minute one-time playtime rewards instead of an escalating-then-repeating 5-minute loop.

**The single biggest architectural reversal: passive income no longer comes from holding items, it comes from *placing* them.** Every prior pass in this game's history has treated "own it, it pays you" as the core loop — this pass deliberately breaks that. Each plot got 5 new physical `PetPad`s (a `Part` + `ProximityPrompt` + `BillboardGui` label each, built right behind the existing fusion pad, clearing its 16-stud footprint) capped by one shared constant, `PET_PAD_COUNT = 5`, that does triple duty as the pad count, the placement cap, and the walk-speed bonus cap. Two new remotes (`PlacePet`, `UnplacePet`) move an item between `s.inventory` and a new `s.placed` array; the passive-income loop and the walk-speed bonus both now sum over `s.placed` instead of `s.inventory`. The old decorative "mirror your whole inventory behind the pad" display from two passes ago — purely cosmetic, never gated anything — was deleted outright (`refreshInventoryDisplay`, `clearInventoryDisplay`, `DISPLAY_COLS`/`DISPLAY_SPACING`/`DISPLAY_START_Z`, all gone) and replaced by `redrawPetPad`/`refreshPlacedPets`, which render only what's actually earning. Un-placing works two ways that share one function (`unplacePet`): clicking a placed slot in the Inventory popup, or walking up to the physical pad and holding the prompt — both end up back in inventory, capacity-checked the same way. The matching carry-side ask ("let me take something off the fuse pad before I commit to fusing it") got its own remote, `RemoveFromCarry`, and turned the old static "CARRYING: [text]" label into per-slot clickable buttons.

**Walk speed changed shape along with everything else:** base speed went 16→22, and the old "+1 per inventory item, capped at +10" bonus became "+2 per *placed* pet, capped at `PET_PAD_COUNT * 2` (=10)" — same cap, differently earned — stacked with a brand new **Speed Boots** upgrade (`+8% move speed per level, level 1-8, 700 coins base, 1.85× growth`) that multiplies the whole sum. Both `s.upgrades` fixtures (the default-data shape and every fallback literal scattered through `onPlayerAdded`/Rebirth) needed the new `speed = 1` field added in lockstep, plus a `upgrades.speed = upgrades.speed or 1` migration line so a save from before this pass doesn't come back with a nil multiplier and error the first time anyone moves.

**The Shop UI is a full replacement, not a patch — `GamepassUI.client.luau` is gone, `ShopUI.client.luau` exists instead.** Rebuilding in place risked leaving two scripts both trying to claim the same right-rail slot 3 nav button; deleting the old script from Studio was part of the sync, not an afterthought. The new panel is a single overlay with a 3-tab bar (PASSES / CODES / PETS) instead of three separate popups. PASSES carries over the original gamepass-purchase logic untouched — same `MarketplaceService` calls, same `Pass_*`/`PassStatus_*` attribute watching — just re-homed into its own tab. CODES is new: a `TextBox` + REDEEM button firing a new `RedeemCode` remote; the server checks a new `ReplicatedStorage/PromoCodes.luau` config table and a per-player `s.redeemedCodes` set (one-time per player, not per-server) before granting a reward, all through the existing toast system for feedback rather than a second round-trip. PETS is also new: a `ReplicatedStorage/ShopPets.luau` config table of coin-purchasable items, deliberately capped to Tier-1 base scrap only (no curated fusion results, no secrets) so buying a "leg up" never bypasses the actual discovery progression, priced at roughly 10x each item's sale value specifically because a placed pet earns forever — a straight sale-price tag would make it an obviously-correct instant buy instead of "skip some grinding." Both new config modules and both new remotes' server handlers (`BuyShopPet`, `RedeemCode`) are genuinely new surface area, not reuses of an existing pattern.

**Three real bugs found and fixed during this pass, in order of how much they would have hurt:**

1. **The whole GameUI script failed to compile the instant it synced to Studio: `Out of local registers when trying to allocate WORLDS: exceeded limit 200`.** Luau caps a script's main chunk at 200 simultaneously-live top-level locals, and this file — which has never used a single `do...end` block anywhere, just one continuous 2000+ line sequence of top-level `local x = Instance.new(...)` statements across every HUD section built up over sixteen prior passes — finally crossed that ceiling the moment this pass's Inventory rewrite alone added ~25 new ones. This is a hard compiler limit, not a style complaint, and it's silent until the exact line that tips it over: nothing about *this specific* new code was wrong in isolation. Fixed by wrapping the two biggest, most self-contained sections (Inventory: ~25 locals; Event Banner + Trading: ~22 locals) in real `do...end` blocks, which let the compiler free those registers at each block's `end` instead of holding all of them live for the rest of the file. The handful of names each block's dispatcher still needs to call afterward (`redrawInventory`/`redrawPlaced`, `redrawTrade`/`myTradeItems`) got predeclared *before* their `do` and assigned without `local` inside — the same "recursive local function" trick already in use for `redrawPlaced` calling itself. Confirmed fixed by computing the worst-case peak register count by hand (≈165, comfortably under 200 with room for future sections) before ever re-syncing, then confirmed for real by a clean Play-mode load with zero compile errors.
2. **A second, purely cosmetic layout bug in the same rewrite: the new PLACE ON PAD button overlapped the "coins/sec" line by 14 pixels**, caught by screenshot rather than assumed away during the same testing pass — a straightforward vertical-spacing miscalculation when the stat panel's internal layout was redesigned for the bigger frame, fixed by shrinking the item viewport 24px and re-deriving every element's Y-offset from the corrected total.
3. **The Shop's new code-entry `TextBox` showed literal text `"TextBox"` instead of the "Enter code" placeholder.** `Instance.new("TextBox")` defaults its `Text` property to the literal string `"TextBox"`, not an empty string the way `PlaceholderText` implicitly assumes — every other `TextBox` already in the game happened to get its `Text` set for some other reason (loaded from data, etc.) and never exposed this. Caught by screenshot, confirmed by direct property inspection (`Text == "TextBox"`, `PlaceholderText == "Enter code"` — both exactly as configured, the property just wasn't the one controlling what showed), fixed with one explicit `codeBox.Text = ""`.

**A `NavButton` module bug caught by reasoning before it ever rendered, not after:** the signature palette's WHITE (assigned to the new SHOP button) would have been unreadable, because `NavButton.luau`'s icon/caption text and outline stroke were hardcoded to white — correct for every accent color the module had ever seen (all dark/saturated enough that white pops), but white-on-white for the one new light accent. Fixed with a small luminance-based `readableTextColor` helper, exported as `NavButton.ReadableTextColor` so ShopUI's own solid-fill tab buttons could reuse the identical logic rather than re-deriving a second, possibly-inconsistent heuristic. The luminance cutoff (0.85) was deliberately tuned *above* GOLD's own luminance (~0.8, the already-shipped, already-tested Rewards button) rather than at a "natural-looking" midpoint like 0.6 — a first attempt at 0.6 would have also flipped GOLD and GREEN over to dark text, silently changing two buttons that were already correct and already tested, just to fix the one that wasn't.

**The leaderboard monument gained a second face, and the existing gold decorative frame needed its geometry rethought to support that.** The frame was built last pass sitting off-center in Z specifically to clear the Front-facing `SurfaceGui` — correct for one face, but exactly backwards for adding a Back-facing one: the same offset that kept it *behind* the board from the front would put it *in front of* the board from the back, occluding the new playtime `SurfaceGui` entirely. Fixed by re-centering the frame on the board's own Z-center and shrinking its thickness to fit entirely *within* the board's own depth (0.7 vs the board's 1.0) — fully embedded, so it can never be closer to a viewer than either face regardless of which side they're standing on, still peeking out at the edges (it's wider in X/Y) exactly as intended. The two faces share one `buildLeaderboardFace(face, title, subtitle, scrollBarColor, formatRow)` constructor now instead of duplicating the ~80-line SurfaceGui/scroll/redraw block twice, parameterized by which of `LeaderboardService`/new sibling module `PlaytimeLeaderboardService` feeds it. `PlaytimeLeaderboardService.luau` is a near-exact structural clone of the existing coins-leaderboard module (same OrderedDataStore pattern, same Init/Record/Snapshot/PushToStore/RefreshIfStale/GetTopCached/Cleanup shape) tracking lifetime minutes played instead of lifetime coins, recorded once per minute alongside the existing playtime-reward tick.

**Playtime rewards changed from "every 5 minutes forever, escalating through a table then repeating the last value" to four fixed one-time checkpoints** (5/15/30/60 minutes, 300/500/800/1500 coins) — a `s.playtimeMilestonesClaimed` set (session-only, intentionally not persisted/not reset by Rebirth, since it's about "staying in this session" not a permanent unlock) replaces the old modulo-based repeating trigger.

# Previous handoff — Player trading (2026-09-13) — needs a real 2-player test before trusting it live

Twelfth pass, closing out the fifth and last item from the researched idea list two passes back — and the one flagged from the start as needing the most careful anti-exploit design, since a trading bug is a duplication or scam bug, not just a visual one.

**Flow:** walk up to another player and press E (a `ProximityPrompt` on every character's `HumanoidRootPart`, same interaction language as grabbing scrap or fusing) to open a shared trade window for both of you — nothing happens to either side's items until both players pick one item and both click CONFIRM, so opening it, even by accident, is harmless. New `ServerScriptService/TradeService.luau` (pure session bookkeeping, no item movement — same shape as the other services) plus the actual validation/execution logic in `PlotManager.server.luau`, which is the only place with direct access to carry slots and plot zones. Scoped to Junkyard items only and one item per side — Brainrot creatures never sit in a carry slot or a placement zone (that island pays out immediately), so there's nothing there to trade, and multi-item bundled trades were cut to keep the surface area small on the highest-risk feature of the five.

**The one rule this whole feature exists to get right: changing your offer resets *both* sides' confirmation, not just your own.** Without that, the classic trade scam is trivial — confirm a good item, wait for the other side to lock in, then swap in something worthless and only re-confirm your own side. `TradeService.SetOffer` clears both players' confirmation unconditionally, every time, closing that off entirely.

**Execution is check-everything-then-move-everything, with no yield in between.** `executeTrade` re-validates both offers are still exactly what was claimed (an item could have been sold or already traded away since it was offered) and that both destinations have room, all before touching a single item — and because nothing in that check path yields, nothing else can run in between and invalidate what was just verified. That ordering is what makes the swap atomic without needing an explicit lock.

**A real correctness bug caught by manually re-tracing the logic, not by running it:** the room-check for a placed-item trade looked at each player's *current* free slots before either item moved — so a player whose zone was completely full could never trade an item in that zone for another of the same kind, even a plain 1-for-1 swap that nets to zero change in slots used (their own outgoing item was about to free the exact slot the incoming one needed). Fixed by having the room-check also credit a player's own outgoing item as an already-free slot when it shares a zone with the incoming one. Not a duplication risk either way — the original version was overly conservative, not unsafe — but it would have made trading placed items nearly useless for anyone whose zones were normally full, which given this game's small zone capacities (2-4 slots) is the common case, not an edge case.

**Testing note, and the reason for the warning in this entry's title: this could only be verified with one real player.** Every remote, guard clause, and the full UI (confirmed via a hand-built fake trade snapshot fired at the real client dispatcher) checked out with zero errors, and the swap logic itself got closer review than anything else this session precisely because it couldn't be run start-to-finish. But there is no way to fabricate a second real `Player` instance from a script — Roblox only creates those for genuine client connections — and `start_stop_play` has no option for multiple simulated clients. **Before relying on this in production, do one real two-player trade** (a second account, a friend, or Roblox Studio's own multi-client Test feature) and confirm both sides end up with the right item and nothing duplicates. This is the one feature from this session that hasn't seen a real end-to-end run.

# Previous handoff — fixed unreadable billboard labels across the whole game (2026-09-11)

Bug report from a real gameplay screenshot: every in-world label — zone signs, plot signs, item name tags — was rendering at once, all the same constant on-screen size regardless of distance, piling into a huge illegible wall of overlapping text. Request: "can we fix how i can read every single pop up in this game."

**Root cause:** none of the `BillboardGui`s in the game had `MaxDistance` set, so Roblox rendered every label in the world at full legible size no matter how far away it was — dozens of overlapping labels stack visually as soon as you can see more than a few items at once, because "distance" never shrinks or culls them the way it would a normal 3D object.

**Fix:** added `MaxDistance` to every billboard-producing helper — `ScrapSpawner.server.luau`'s `addLabel`, `PlotManager.server.luau`'s `makeLabel`, and `BrainrotService.luau`'s `label` — so a label only renders once you're actually close enough to read it, and disappears once you walk away instead of staying pinned to your screen from across the map.

**The tuning trap, worth remembering:** `BillboardGui.MaxDistance` is measured from the **Camera**, not the character. Roblox's default third-person camera trails noticeably behind the character (confirmed: ~12 studs back, ~4-5 studs up), so a `MaxDistance` picked by eyeballing "how far should this be readable from the character" will cut labels off well before the player expects, including sometimes standing right next to the thing. Every value in this pass got a deliberate headroom bump over the first-guess number once this was caught (slot labels 25→50, zone signs 40→60, pad labels 40→55, plot sign 70→90, BrainrotService pad 40→55, gates 55→70, items 30→45, ScrapSpawner drops 35→45). If another billboard gets added later, size its `MaxDistance` off actual camera-to-part distance (read `workspace.CurrentCamera.CFrame.Position`), not character-to-part distance.

**Tooling limitation discovered this session, important for whoever tests billboard changes next: `screen_capture` does not reliably show `BillboardGui` text at all.** Every property was independently verified correct via direct instance inspection — `Enabled`, `Visible`, `Text`, `TextTransparency=0`, `BackgroundTransparency=1`, `ZIndex`, `StudsOffset`, and `MaxDistance` checked against the *actual* `workspace.CurrentCamera` distance (not assumed) — across three different labels, in a freshly-restarted Play session with a normal, correctly-tracking third-person camera, at close unobstructed range (as close as ~12 studs with a 90-stud `MaxDistance`). Every one of those screenshots showed no billboard text whatsoever, including on a plot-sign label that was never touched by this fix. Console output was completely clean throughout — no rendering warnings or errors. Also separately discovered: passing `camera_position`/`look_at_position` to `screen_capture` can leave `workspace.CurrentCamera` stuck at the override position afterward instead of resuming normal follow behavior (confirmed via direct `CFrame` inspection — the camera sat ~12 studs from a character that had moved, not tracking it), which further pollutes any subsequent un-overridden screenshot in the same session. Given the user's own original bug-report screenshot was taken through a real Roblox client and clearly shows billboards rendering (that's *why* the overlap was visible at all), the most consistent explanation is that this MCP's screenshot path just doesn't composite the `BillboardGui` render layer, rather than every label in the game being silently broken. **Practical upshot: don't trust `screen_capture` to confirm or deny `BillboardGui` visibility. Verify billboard changes via direct property/distance inspection (`execute_luau`), and have the user eyeball the actual result in their own Play session before treating it as confirmed.**

# Previous handoff — placement economy: passive income + tiered zones (2026-09-11)

The core loop changed: fusing no longer puts the result on a single pedestal for one manual sell. Instead it **auto-places into one of three zones on your plot**, based on tier, where it earns coins every few seconds for as long as it stays — sell it anytime instead for an instant (smaller) payout. This replaces the "fuse → sell → repeat" loop with "fuse → build a collection → passive income scales with how many rare things you've placed."

**Zones** (physically built into each of the 8 plots, behind the fusion pad): `GARAGE` (Tier 2, 4 slots), `WORKSHOP` (Tier 3 non-secret, 3 slots), `TROPHY CASE` (Tier 4+ and all secrets regardless of tier, 2 slots). A result auto-places into the first empty slot of its zone; if that zone is full, the result drops back into the shared yard instead of being lost, with a toast telling the player to clear a slot.

**Income formula:** each placed item earns `value / 90` coins/sec (a `PLACEMENT_PAYBACK_SECONDS` constant — roughly how long it takes passive income to match a manual sell, after which it's pure profit for as long as it's placed). The Haggler upgrade and the timed 2x-sell boost both apply to this rate too, not just manual sells (see `valueMultiplier` in PlotManager). Income is credited server-side every 3 seconds (`INCOME_TICK_SECONDS`) by summing all filled slots across a player's zones.

**Persistence:** `DataManager`'s default save data gained a `placed` field — a list of `{zone, slot, itemName, value}` records, written by `snapshotPlaced` (in the same autosave/leave/shutdown paths as everything else) and restored on join by re-rendering each saved slot. Old saves without this field default to `{}` via the existing "fill in any field a newer version added" merge, so no migration was needed.

**Regression caught and fixed:** removing the single "Pedestal" part broke `MapRevamp.DressPlot`'s `plot:WaitForChild("Pedestal", 10)` dependency (a 10s no-op wait, not a crash, but per-plot cosmetic dressing — pad color, trim — silently stopped applying). Fixed: `DressPlot` now trims the three zone sign posts instead of the old pedestal, and `MapBootstrap` waits on `garageSign` instead of `Pedestal`. Worth remembering: MapRevamp/MapBootstrap look up PlotManager's part names by string, so future PlotManager renames should grep MapRevamp for the old name first.

**Verified in Studio Play**, end to end, via actual ProximityPrompt-triggered gameplay (not just command-bar calls): grabbed real items, fused a valid Tier 2 recipe, confirmed it rendered in the correct zone slot with the correct coins/sec label, watched the coin count actually increase over several seconds from passive income alone, sold a placed item via its own prompt and confirmed the slot cleared, then **stopped and restarted Play** and confirmed the placed item was restored from the save data into the same slot. No console errors at any point. Not tested: multiple concurrent players, a zone actually filling up (the "returned to the yard" full-zone path), and the live published game.

Tuning knobs if the economy feels off: `PLACEMENT_PAYBACK_SECONDS`, `INCOME_TICK_SECONDS`, and each zone's `capacity` are all in the `ZONES` table / constants near the top of `PlotManager.server.luau`.
